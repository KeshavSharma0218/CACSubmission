# SafeWalk Backend

Backend API for SafeWalk — a pedestrian routing service that optimizes for **safety**
(lighting, sidewalks, crime data, crowdsourced hazard reports) rather than pure
distance or speed. Built with FastAPI, SQLAlchemy 2.x (async), and PostgreSQL/PostGIS.

The backend now includes the complete first release: PostGIS persistence and
migrations, external service clients, explainable route safety scoring, OSRM-based
candidate routing, the Android-facing REST API, JWT preparation, safe error handling,
and inbound rate limiting.

## Running it — two ways

Docker isn't required. Pick whichever is more convenient:

### Option A: Docker Compose (bundles a matching PostGIS instance)

```bash
cp .env.example .env      # fill in real values (JWT secret, etc.)
docker compose up --build
```

API comes up at `http://localhost:8000`, Postgres/PostGIS at `localhost:5432`.
Compose applies `alembic upgrade head` before starting Uvicorn.

### Option B: Plain Python (uv), against any Postgres/PostGIS you already have

Works against a local Postgres install, or a free hosted PostGIS database (e.g.
Neon or Supabase both offer free tiers with PostGIS enabled) — just point
`DATABASE_URL` at it.

```bash
uv venv
uv pip install -e ".[dev]"
cp .env.example .env      # set DATABASE_URL to point at your Postgres instance
uv run alembic upgrade head
uv run uvicorn app.main:app --reload
```

Either way, once it's running:

- `GET /docs` — interactive OpenAPI docs (auto-generated by FastAPI)
- `GET /api/v1/health` — health check, reports API + DB status
- `POST /api/v1/route` — route candidates scored for safety, distance, walking time, warnings
- `GET /api/v1/geocode` and `GET /api/v1/reverse-geocode` — address lookup
- `POST /api/v1/report` — anonymous or optionally JWT-associated hazard report

## Running tests

```bash
uv run pytest
```

Repository integration tests automatically run when a disposable PostGIS DSN is set:

```bash
TEST_DATABASE_URL="$DATABASE_URL" uv run pytest tests/test_repositories_postgis.py
```

## Project structure

```
backend/
  app/
    main.py              # FastAPI app: lifespan, CORS, global exception handling, router mounting
    api/
      routes.py           # versioned router aggregation and health check
      routing.py          # route and geocoding transport adapters
      reports.py          # crowdsourced report transport adapter
    services/              # provider clients, route planning, and safety composition
    database/
      database.py          # async engine, session factory, PostGIS extension bootstrap
      models.py             # SQLAlchemy/PostGIS domain models
      schemas.py            # Pydantic request/response schemas
      repositories.py       # async data-access layer
    routing/                # route geometry helpers and polyline encoding
    utils/
      config.py            # Pydantic Settings — all external config lives here, no hardcoded secrets
      logging.py           # structlog-based structured logging
  tests/
    test_health.py
  docker-compose.yml
  Dockerfile
  pyproject.toml
  .env.example
```

## Why these architectural choices

- **Async everywhere.** Route handlers, DB sessions, and (in later steps) calls to
  Overpass/Nominatim/OSRM/weather/crime APIs are all `async`. Route computation
  naturally fans out into several concurrent external calls; blocking I/O would
  serialize them for no reason.
- **Config is centralized and env-driven** (`app/utils/config.py`). No API keys or
  DSNs are hardcoded. This also means the same code can point at the public
  Nominatim/Overpass instances in development and self-hosted or commercial
  equivalents in production, without a code change — see the note on rate limits
  below.
- **The DB layer is a plain dependency (`get_db`), not a global.** Every request gets
  its own session with a clean transaction boundary — no state leaks between
  concurrent requests.
- **PostGIS extension is ensured at startup**, not left as a manual setup step, so a
  fresh database (Docker or otherwise) is immediately usable.
- **Global exception handlers** ensure raw exceptions (stack traces, DB error text)
  never reach the client — they're logged with full detail, and the client gets a
  generic, safe message. This is a project requirement, not just good practice, since
  the API is consumed directly by the Android app.

## Upstream and inbound rate limits

- **Nominatim**'s public instance enforces a hard 1 request/second limit, requires an
  identifying `User-Agent` (already wired into config), and forbids bulk/systematic
  queries. Fine for interactive geocode/reverse-geocode calls triggered by a user
  action; not something to lean on for bulk data loading.
- **Overpass**'s public instance is fine for occasional queries but not for scheduled
  or bulk ingestion (e.g. pulling all sidewalks/streetlights for a city) — that kind
  of job should run against a self-hosted Overpass instance. `OVERPASS_BASE_URL` is
  already just a config value so this swap won't require code changes later.

Both are reflected in `.env.example` as swappable URLs, not hardcoded endpoints.
Nominatim calls are serialized and throttled, all external GETs have explicit
timeouts and bounded retries, and upstream failures become sanitized domain errors.
The API also applies a configurable per-process IP limit (default 60/minute), which
is suitable for a single free-tier process; multi-instance deployment should replace
it with a shared gateway or Redis-backed limiter.

## Future work

The intended next phase is enforced account authentication, ingestion/background
jobs for OSM and crime datasets, shared caching/rate limiting for multi-instance
hosting, and richer data sources for traffic, visibility, and user-report factors.
SafeWalk no longer uses a custom A* provider; it requests multiple OSRM walking-route
candidates and scores them with live OSM, weather, crime, and report data.
